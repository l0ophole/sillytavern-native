# SillyTavern C/C++ Port — v0.1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a native GTK3 C++17 SillyTavern-compatible desktop app on Linux that imports character cards, streams OpenAI-compatible chat replies, and persists chats, with a `make menuconfig` feature tree.

**Architecture:** A GTK-free `libstcore` owns data formats, settings, prompt assembly, HTTP/SSE, and the OpenAI client. A gtkmm-3.0 UI layer owns windows, dialogs, and dispatcher-marshalled streaming updates. A registry-driven ncurses tool writes `.config` and `build/features.h`; planned features stay visible but unselectable.

**Tech Stack:** C++17, gtkmm-3.0, libcurl, ncursesw, GNU Make, vendored `nlohmann/json`, Xorg/Xvfb, Docker for Alpine verification.

**Spec:** `docs/superpowers/specs/2026-11-01-sillytavern-cpp-port-design.md`

## Global Constraints

- C++17, no Node.js, no WebKit, no embedded original frontend.
- Linux only; must run under Xorg.
- Must build on Arch Linux (glibc) and Alpine Linux (musl).
- `make` must build; `make menuconfig` must configure.
- Unported features must be visible but dim and unselectable in menuconfig.
- Critical v0.1 features are locked on once ported.
- Never write into `SillyTavern/`; import copies data.
- All writes stay under XDG config/data roots; filenames sanitized.
- One descriptive git commit per ported feature, immediately after verification.
- Plans live in `docs/plans/`; never delete them.
- `docs/PORT_LOG.md` is updated for every feature and stage.
- Unit tests, integration tests, Xvfb smoke test, and Alpine build are required evidence.

## Review Focus

These are the failure modes most likely to hurt a real user, and each gets a test in the owning task:

1. A PNG card with both `ccv3` and `chara` must use `ccv3`; a malformed or missing tEXt chunk must produce a clear error, never a crash.
2. A chat filename or card name containing `../`, absolute paths, control characters, or a name collision must never escape the data directory or overwrite another file.
3. A streaming reply split at arbitrary byte boundaries (including mid-UTF-8 and mid-SSE line) must produce the exact same text as one contiguous stream.
4. An HTTP error, TLS failure, timeout, or user cancel must not lose already-received text or leave the UI stuck in a generating state.
5. Restarting the app after saving a chat must preserve message order, roles, timestamps, unknown JSON fields, and the configured user name.

## 3. Stage acceptance gates

A stage is complete only when all of these are true:

- the stage plan exists and is committed before implementation;
- every task's tests fail before implementation and pass afterward;
- `make` succeeds from a clean tree;
- `make test` passes;
- no feature is marked `ported` until its UI/core portion is complete;
- `docs/PORT_LOG.md` has a row for every feature touched;
- `features/features.json` status is updated and `docs/FEATURES.md` regenerated;
- the feature commit is made immediately after verification;
- `git status` is clean.

## 4. Definition of done for v0.1

1. `make menuconfig` shows 105 features; 19 ported critical features are enabled and locked; 86 planned features are dim and unselectable.
2. `make` builds on Arch and Alpine.
3. `make test` passes all unit tests and the mock OpenAI integration test.
4. `xvfb-run -a ./build/sillytavern-port --smoke-test` exits 0.
5. A PNG character card imports and displays.
6. A chat streams from the mock server, survives restart, and preserves order/roles/unknown fields.
7. Editing, deleting, regenerating, and continuing messages work.
8. The original `SillyTavern/` directory is untouched.
9. Every v0.1 feature has a plan, log entry, test evidence, and commit.

## 5. Execution rules

- Write the stage plan immediately before starting that stage. Do not delete old
  stage plans.
- Use TDD for every core module: write the failing test, run it, implement the
  minimal code, run it, then commit.
- Keep `libstcore` free of GTK includes.
- Prefer `std::filesystem` and POSIX `open/fsync/rename` for atomic writes.
- All user-facing strings are plain ASCII in v0.1; i18n is deferred.
- Log errors with the API key redacted.
- Never commit `.config`, `build/`, runtime data, or the upstream checkout.
- If a stage reveals a spec gap, stop and update the spec before coding around it.
